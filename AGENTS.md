# Постоянные правила работы со спецификацией

## Назначение и границы

Репозиторий предназначен для проектирования целевой информационной системы юридической фирмы, занимающейся банкротством физических лиц и связанными услугами. В дальнейшем поверх этой модели будут работать оркестратор процессов, AI-агенты, сотрудники, интеграции, Bitrix, внешние государственные и юридические системы.

Сейчас проектируется спецификация, а не реализуется production-система.

## Правила

1. Git-репозиторий является source of truth — единым источником истины для архитектуры, бизнес-процессов и модели данных.

2. Использовать три статуса информации:
   - [AS-IS] — подтвержденное текущее поведение компании/Bitrix.
   - [TO-BE] — предлагаемая целевая архитектура или процесс.
   - [?] — информации недостаточно, требуется проверка.
   Никогда не превращать [?] в факт без новых данных.

3. Не моделировать бизнес только через стадии Bitrix. Bitrix является одной из интеграций/legacy-систем. Каноническая модель должна описывать реальный бизнес-домен.

4. Один клиент может одновременно иметь несколько услуг и несколько параллельных процессов.

5. Процессы должны поддерживать ветвления, параллельное выполнение, возвраты, повторные попытки, ошибки, исключения, ручные проверки, автоматические действия, завершение и отмену.

6. Для каждого подробного процесса по возможности фиксировать:
   - входные условия;
   - READ DB;
   - WRITE DB;
   - документы;
   - внешние источники;
   - действия Bitrix;
   - автоматизации;
   - задачи;
   - параллельные процессы;
   - решения;
   - риски;
   - события;
   - условия выхода;
   - следующие процессы.

7. Каждое существенное изменение состояния должно быть представимо системным событием. Примеры имен событий: document.received, document.verified, task.created, task.completed, court.application.filed, asset.detected. Это примеры, а не подтвержденный каталог событий компании.

8. Исторические данные не должны бесследно перезаписываться. Учитывать versioning, timestamps, source и audit trail: версии, временные отметки, источник и историю изменений.

9. Документы и записи звонков не предполагается хранить бинарно в основной БД. В БД проектировать метаданные и ссылки на object storage.

10. Факт, вывод AI и бизнес-решение являются разными сущностями. Не смешивать их.

11. AI-агенты не должны напрямую изменять PostgreSQL. В будущей архитектуре изменение доменных данных предполагается через контролируемый Domain API/commands.

12. Любое новое поле БД должно иметь понятную бизнес-причину появления. По возможности фиксировать:
    - entity — сущность;
    - field — поле;
    - type — тип;
    - business meaning — бизнес-смысл;
    - source — источник;
    - required condition — условие обязательности;
    - writer — кто записывает значение;
    - consumers — потребители.

13. Для визуальных моделей использовать Mermaid. Не помещать всю систему в одну гигантскую диаграмму. Использовать отдельные представления:
    - master process;
    - detailed processes;
    - ERD;
    - state models;
    - event models;
    - integrations;
    - agent interactions.

14. Подробный Data Dictionary хранить отдельно от Mermaid, в data/dictionary/.

15. Не помещать в репозиторий реальные персональные данные клиентов, документы клиентов, пароли, токены, API keys и другие secrets.

16. При обнаружении неизвестного бизнес-правила добавлять его с отметкой [?] в gaps/open-questions.md, а не придумывать ответ.

17. Не удалять подтвержденную информацию при рефакторинге без явной причины.

## Текущий этап работы

В рамках начальной подготовки репозитория не создавать бизнес-процессы, ERD или таблицы БД. Их проектирование выполняется по отдельному последующему заданию. Не выполнять git commit без разрешения пользователя.
